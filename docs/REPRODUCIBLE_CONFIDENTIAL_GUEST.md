# Reproducible confidential guest chain

This document separates reproducible artifacts from runtime attestation. A
byte-identical image is useful reference data; it is not evidence that one
running VM loaded or enforced that image.

The intended relying-party chain is:

```text
source + lockfile + pinned toolchain
  -> static supervisor ELF
  -> deterministic ext4 + appended dm-verity tree
  -> VMM/libkrun/firmware/kernel/initrd/cmdline launch manifest
  -> offline SNP/TDX/Nitro reference values
  -> signed build provenance and published manifest
  -> fresh hardware evidence + guest-key possession
  -> verify-before-encrypt or appraisal-gated secret release
```

Every arrow is load-bearing. In particular, hashing an OCI name, model name,
or read-only ext4 file does not prove that the guest which handled plaintext
used those bytes.

## Implemented artifact stage

`scripts/build-reproducible-vm-guest.sh` builds the minimal static supervisor
with:

- exact Rust 1.97.1 compiler commit
  `8bab26f4f68e0e26f0bb7960be334d5b520ea452`;
- `Cargo.lock` and `--locked` dependency resolution;
- a release-derived profile with one codegen unit, fat LTO, aborting panics,
  disabled incremental compilation, and stripped symbols;
- `SOURCE_DATE_EPOCH=0`, repository path remapping, and no ELF build ID; and
- an explicit musl target.

Build twice into independent target directories and compare:

```console
./scripts/build-reproducible-vm-guest.sh \
  aarch64-unknown-linux-musl target/reproducible-a
./scripts/build-reproducible-vm-guest.sh \
  aarch64-unknown-linux-musl target/reproducible-b
cmp \
  target/reproducible-a/aarch64-unknown-linux-musl/reproducible-guest/nanocodex-vm-guest \
  target/reproducible-b/aarch64-unknown-linux-musl/reproducible-guest/nanocodex-vm-guest
```

`GuestRuntimeDisk::prepare` then creates a bit-identical authenticated root for
identical supervisor bytes. It fixes the ext4 label, derives an RFC 9562
version-8 UUID from the supervisor digest, uses epoch timestamps for explicit
files, normalizes the formatter's implicit root and `lost+found` inode
timestamps, and validates the filesystem contents. It hashes all 32,768 4 KiB
data blocks with dm-verity format 1 and a deterministic domain-separated salt,
then appends the no-superblock SHA-256 tree root-first. The resulting device is
135,278,592 bytes: 128 MiB of ext4 followed by 259 hash blocks.

Publish a root and strict `GuestImageManifestV1` with:

```console
just build-reproducible-guest-image \
  target/reproducible-a/aarch64-unknown-linux-musl/reproducible-guest/nanocodex-vm-guest \
  output/reproducible-guest
```

The output `guest-root.ext4.verity` and manifest contain no timestamp or host
path. The manifest records the target architecture, supervisor
path/length/SHA-256, ext4 UUID/label/length/SHA-256, exact dm-verity table and
trusted root hash, and complete root-device length/SHA-256. Unknown fields,
unsupported versions, invalid digests, unsupported architectures, inconsistent
UUIDs, salt derivations, and verity geometry are rejected. Cache recovery also
recomputes the tree and replaces same-sized tree corruption.

The generated bytes are compatible with Linux `veritysetup verify` using
format 1, 4 KiB data and hash blocks, 32,768 data blocks, no superblock, and a
134,217,728-byte hash offset. The root hash and salt come from the manifest;
the root hash is trusted only after the measured-launch policy authenticates
it.

This artifact manifest is not the workload manifest used for a production
attestation decision. Generating a correct tree does not prove that one running
guest selected or enforced it.

## Complete measured-launch manifest contract

`host::MeasuredGuestManifestV1` is the strict canonical preimage for hardware
attestation, appraisal, and secret-release policy. Version one requires:

- source repository and revision, `Cargo.lock` digest, compiler commit, and
  target triple;
- exact VMM, libkrun, firmware, kernel, initrd, supervisor, and root-image
  file identities;
- canonical filesystem UUID and a complete dm-verity table identity;
- CPU TEE, vCPU count, memory, kernel command line, network policy, disabled
  debug, and disabled migration;
- a sorted, duplicate-free list of every plaintext-handling application-code,
  OCI-image, model-weight, and configuration identity plus exact argv; and
- CPU-specific offline reference values: an SNP launch measurement for the
  selected vCPU count, all owned TDX registers and pre-workload RTMR3, or an
  exact Nitro PCR map.

The type has no plain-read-only-root constructor. It requires dm-verity because
an untrusted host can alter or equivocate an ordinary block device after launch.
It also requires the exact supervisor to appear in the plaintext-handling
component set. This prevents a manifest from pinning only a trusted base image
while leaving the application or model outside the attested surface.

Canonical compact JSON is hashed under
`nanocodex-vm-measured-guest-manifest-v1`. Changing source, firmware, kernel,
initrd, command line, root hash, supervisor, application/container/model
identity, resources, or platform reference values changes the commitment.

## Remaining enforcement work

Nanocodex now rejects a plain ext4 root for every confidential profile. An
`AuthenticatedExt4` configuration emits a deterministic, launch-measured
`dm-mod.create` table for `/dev/vda`, waits for that device, selects
`/dev/dm-0`, and attaches the host image read-only. It also requires libkrun's
`TEE_AUTHENTICATED_ROOT` feature. Nanocodex pins
`gakonst/libkrun@220e328ef34a7ede8fedbf703071eabec5844b45`, whose TEE init accepts
only `/dev/dm-0` when authenticated-root policy is present and otherwise fails
closed.

The matching firmware source is pinned to
`gakonst/libkrunfw@5c2a7dd1d1bf62a8773e1e4dfac06b240cc5fe10`.
Build either dedicated variant in the pinned Debian x86_64 environment with:

```console
just build-confidential-libkrunfw sev output/libkrunfw-sev
just build-confidential-libkrunfw tdx output/libkrunfw-tdx
```

The recipe pins the builder image, Debian snapshot, source revision, and Linux
6.12.91 tarball digest. It verifies built-in `DM_INIT`, `DM_VERITY`, device
mapper, and SHA-256 support, then retains the firmware library, embedded
kernel, initrd, qboot image, resolved configuration, and a compact digest
manifest. SEV and TDX are built separately and cannot be feature-unified.

Two independent SEV builds in the pinned environment were byte-identical on
2026-08-11. Their compact manifest SHA-256 is
`d48c93bcced73ef21e5137f03e5690aa6a7247bea0ebc1e521a36d0f8cdfd144`;
the firmware SHA-256 is
`83c23bd3ca865fa8fbb5cc8cf7836772adc1d07395cf56399aca44038e6b8684`;
and the retained `vmlinux` SHA-256 is
`653cb124e8c6f74b10be72de098045ecda68f37ef2544eb98e7624277b3ee772`.

Two independent TDX builds in the pinned environment were also byte-identical
on 2026-08-11 across the firmware library, retained kernel, initrd, qboot,
source and resolved configurations, and compact manifest. Their compact
manifest SHA-256 is
`d6e7abe590e8168fa6fd17c9fe9fddcd1141a3eb541d772b18337f2f56572fcb`,
firmware SHA-256
`1efbad95a9d83b49eec6825d8d0e9099627d11822ba926aa9e52bd54a572f419`,
and retained `vmlinux` SHA-256
`787f2b6646e6ded366e15705ca540ec82917ba918b58772d0c64783292a6ea9c`.

The following must still land before the manifest can authorize a production
secret:

1. Reproduce and publish the matching SEV and TDX manifests and binaries from
   an independent external builder.
2. Use the retained exact firmware-embedded kernel and initrd artifacts to
   compute the manifest's SNP/TDX reference values offline.
3. Run positive boot plus root, tree, table, supervisor, model, argv, nonce,
   key, debug, migration, and
   reference-value tamper cases on real hardware.

Until then, the reproducible authenticated-root output is a deterministic build
artifact and cache input. `HOST_DATA` and TDX RTMR3 can bind a manifest
commitment, but a guest loaded without selecting the manifest's dm-verity
mapping could still lie about what it enforced.

## Provenance and public verification

Reproducibility lets an auditor rebuild a published artifact. Provenance tells
the auditor which source and builder claim to have produced it. The publication
stage should wrap the canonical manifest digest in signed SLSA provenance,
publish the signature and certificate, and use a transparency log so release
history cannot be silently rewritten. Provenance must remain an envelope around
the measured manifest rather than a field inside it; otherwise adding a build
signature would recursively change the value being signed.

A third-party verification package must be able to fetch the manifest, raw
hardware evidence, endorsements/collateral, key-possession proof, and signed
receipt; validate them without operator-only state; and reproduce the exact
application/model preimage. A green coordinator flag or a server-reported
container ID is not a substitute for those artifacts.
